# PTAR Decision Log

Maintained per [Development_Protocol.txt](Development_Protocol.txt) Section 2. This log records *why* material decisions were made and how they evolved. It is distinct from [PTAR_Rebaseline_Spec.md](PTAR_Rebaseline_Spec.md) (*what* the system must do) — do not merge the two, and do not reconstruct this log from memory; append to it as decisions are made.

Each entry captures: the decision, why it was made, the evidence/requirement/constraint that drove it, its status (confirmed / provisional / open-dependent), and what earlier entry (if any) it supersedes.

Never silently overwrite or reinterpret an existing entry. If new evidence conflicts with one, add a new entry that states the conflict explicitly and points back at the entry it revises — never edit history in place.

## Active overrides index

### DL-001 — Block Start/Resume during any active traversal phase

- **Follow-up finding and fix, 2026-09-28 (usability, surfaced by testing the diagnostic edge case above).** The block message was a one-shot `say()` call, so it got silently overwritten within a couple of seconds by the traversal's own routine progress narration (e.g. `WATER DROP LANDED`, `Facing underwater target`) — functionally useless as an explanation of why Start/Resume/Use-Nearest did nothing, even though the guard itself worked correctly (developer's own words: "it was functionally useless"). **Fix:** reused the exact pattern already built for DL-013's TAC block. New runner method `traversal_blocking()` (`TRAVERSAL_PHASES[self.phase]==true`), live-recomputed every call from `phase`, never from the transient `message`. `PTAR.lua` grays Start/Use Nearest Waypoint/Resume (`ImGui.BeginDisabled`/`EndDisabled`) and shows a persistent yellow explanation line whenever either `tac_busy()` or `traversal_blocking()` is true; Pause and Stop stay enabled either way. Shipped as `v0.2.0-test.24`.
  - **Local/simulated evidence:** 4 new tests (true during each of the 7 phases; false outside them; stays true across several routine progress messages that previously would have overwritten the old note; clears once the traversal is actually left, i.e. `Completed`) — all mutation-checked (an always-true and an always-false mutant were both caught). A one-off diagnostic against a stubbed ImGui confirmed the runner-side logic and message selection, but stubbed ImGui can't prove the real client renders `BeginDisabled`/`TextColored` correctly.
  - **Live-verified, 2026-09-28** (screenshot + developer confirmation, `v0.2.0-test.24`, phase `traverse_falling`): the yellow line "PTAR is mid-traversal (phase: traverse_falling). Start, Use Nearest Waypoint and Resume are unavailable..." was visible and still showing as the fall actively progressed (not a one-instant flash); Start, Use Nearest Waypoint and Resume all rendered in the same dimmed/disabled shade; Pause and Stop rendered normally, confirming they stayed enabled. **This also resolves DL-013's previously-open "`ImGui.BeginDisabled` inside PTAR" unverified item** — it's the identical mechanism, now confirmed working in the real client for both the traversal and TAC cases.
  - **Supersedes:** nothing in the original decision; this only fixes how its already-correct outcome is communicated.

- **Status:** Live-verified, PASS on all 3 planned scenarios — see test evidence below. **The diagnostic edge case (below) is also now live-verified PASS, 2026-09-28** — DL-001 has no remaining untested paths. Version confirmed as `v0.2.0-test.19` by the developer's own observation of the window title during the test session (the log itself carries no version stamp yet; that's DL-002, not built).
- **Test build identity:** Shipped under version `v0.2.0-test.19` (bumped from `test.18`, manually, in both `PTAR.lua` and `PTAREditor.lua` — the single-authoritative-version-source work is still DL-002, not yet done).
- **Test evidence (live, 2026-09-27, character `Kateri`, zone `sleeper`, log `PTAR_multiclass_Kateri.log`):**
  - **Test 1 (guard fires) — PASS, observed twice.** `18:04:23.970` and `18:04:29.652`: `status=Error, phase=traverse_approach` → `Error: Start/Resume blocked: still in traversal phase traverse_approach...`. `18:05:39.926` and `18:05:40.038`: `status=Paused, phase=traverse_falling` → `Paused: Start/Resume blocked: still in traversal phase traverse_falling...`. In both windows the log shows only `PATH` lookups (from `self:nearest()`) immediately followed by the block message — no `/nav` command logged.
  - **Test 3 (Stop clears the guard) — PASS, full resumption not just no-block.** `18:05:41.803`: `Ready: Stopped...`; next `TICK` line confirms `phase=nil`. `18:05:44.638`–`.642`: Start issued `/nav locyxz -2383.676 -786.439 -988.873 dist=15` and `Running: #43 Warder Door Loc` — genuinely resumed, not merely unblocked.
  - **Test 2 (no over-blocking) — PASS.** `18:05:44.313`: Paused during `phase=nav` on waypoint #43. ~13s later, Start/Resume re-issued `/nav` to the same waypoint and resumed cleanly — no block message.
  - **Observed diagnostic edge case, fixed as a follow-up:** `18:05:13.520`, still in `phase=traverse_falling`, "Use Nearest Waypoint" produced the older, pre-existing `Error: No reachable dry waypoint near your elevation...` instead of the new traversal-block message. Cause: `self:start_nearest()` called `self:nearest()` *before* `self:start()`; when `nearest()` itself found zero candidate waypoints, it failed and returned before the guard (which lived only in `self:start()`) was ever reached. No navigation was attempted either way, so this was safe, but the message in that specific sub-case (mid-traversal *and* nothing else currently reachable) didn't name the traversal phase as the reason. **Fixed:** the check is now a shared local `traversal_blocked()` helper, called at the top of both `self:start()` and `self:start_nearest()` — so it fires before `self:nearest()` runs, and "Use Nearest Waypoint"/Resume always show the specific traversal-block message when applicable, regardless of whether any other waypoint happens to be reachable. Not yet live-verified — this specific sub-case (mid-traversal with zero other reachable waypoints) is narrow and wasn't re-tested after the fix. **Live-verified 2026-09-28**: `PTAR_multiclass_Erebeth.log`, `21:38:26.464`, phase=`traverse_falling`, "Use Nearest Waypoint" pressed -> correctly produced `Start/Resume blocked: still in traversal phase traverse_falling...`, not the old generic message. Closes this edge case; the guard fires unconditionally before any reachability search runs, so the zero-other-waypoints condition no longer matters to the outcome.
- **Decision:** Start and Resume must refuse to act whenever the runner's current phase is any traversal/water phase (`traverse_facing`, `traverse_approach`, `traverse_falling`, `water_facing`, `water_descend`, `water_cross`, `water_ascend`), not only mid-fall/mid-swim.
- **Why / evidence:** Every traversal phase occurs, by definition, in a location with no navmesh coverage (spec §7, §16). Without this guard, Start/Resume halts movement and then attempts to navigate to an unreachable point, producing an immediate, avoidable Error. The guard exists in the design (spec §8, §16) but the gap was confirmed against current code — traversal support was added after the original Start/Resume guardrails were designed, and those guardrails were never revisited against the new phase set.
- **Implementation notes:** Guarded in [PTARRunnerCore.lua](../lua/PTAR/PTARRunnerCore.lua) `self:start()`, which `self:resume()` and `self:start_nearest()` (the "Use Nearest Waypoint" button) both already route through — so a single guard point covers Start, Resume, and Use Nearest Waypoint, since all three share identical navigate-to-unreachable-point risk. Two additions beyond the literal spec text, required for the guard to be correct rather than merely present (Development Protocol §3 — necessary for correct implementation of the agreed behavior, not new scope):
  - `advance()` now clears `self.phase` before evaluating `manual_handoff`/finish, because a traverse waypoint whose exit is already within radius can reach `advance()` directly from a traversal phase (e.g. `traverse_falling`) without passing through `navigate()` first. Without this, a traversal waypoint flagged `manual_handoff` (or similar direct-advance cases) would leave `self.phase` permanently stuck on a traversal value even after reaching a terminal status, incorrectly blocking a later legitimate Start.
  - `self:stop()` now clears `self.phase`, since spec §10 treats Stop's resulting `Ready` status as a full reset to a clean startable state; leaving a stale traversal phase behind after an explicit Stop would otherwise permanently lock out Start via this new guard.
  - `self:pause()` was deliberately left untouched — `self.phase` must survive Pause for this guard to have anything to check on Resume.
- **Supersedes:** none.
- **Source:** [PTAR_Rebaseline_Spec.md](PTAR_Rebaseline_Spec.md) §8, §16, §21 (item 1).

### DL-002 — MQ-console echo toggle, per-line version stamping, single authoritative version source

- **Status:** Implemented together with DL-003 (developer chose not to split them, since the echo toggle's persistence half is genuinely coupled to DL-003). **Live-verified, PASS**, 2026-09-27, against `v0.2.0-test.20` — developer confirmed the test passed (no detailed log walkthrough recorded for this one, unlike DL-001's dedicated test plan).
- **Decision:** (a) Add a new UI toggle controlling only whether DEBUG-level log lines are also echoed to the in-game MQ console (file logging unaffected either way); default on in test builds, off in release/RC builds, but any persisted user preference always wins over the build default. (b) Every log line must include the running build's version number. (c) Version identity must be derived from a single authoritative internal value, replacing the current hardcoded per-window literal strings.
- **Found during implementation, folded in as part of the same paragraph's intent (not a separate decision):** spec §12 also states file logging must *always* write DEBUG-level lines, in every build, with no toggle to reduce it — "this replaces the current code's behavior of skipping DEBUG-level file writes when a Verbose toggle is off." The existing "Verbose Debug: ON/OFF" button was exactly that behavior. Per the spec, the same button is repurposed to mean the new MQ-console-echo toggle instead, and file writes are unconditional now — this wasn't its own DL-002/DL-003 bullet, but doesn't make sense to implement separately from the button it repurposes. Confirmed with the developer before implementing.
- **Implementation:**
  - New [PTARVersion.lua](../lua/PTAR/PTARVersion.lua): `VERSION` string, `is_test()` (checks for a `-test.` pre-release segment). Required by `PTAR.lua`, `PTAREditor.lua` (both window titles), and `PTARLog.lua`.
  - [PTARLog.lua](../lua/PTAR/PTARLog.lua) rewritten: constructor now takes `version` and an `echo_fn` callback; every line is stamped with the version; the old `if level=='DEBUG' and not self.verbose then return end` file-write gate is removed entirely (file always gets everything); a new independent `echo` flag (`set_echo`) controls only whether a DEBUG line is also passed to `echo_fn` (wrapped in `pcall`, since a console-print failure must never break file logging). **EVENT-level lines are never console-echoed** — the toggle only ever applies to DEBUG, matching the spec text literally (EVENT/status is already visible in the ImGui window itself, so nothing is lost).
  - `PTAR.lua`: owns `echo_fn` (`mq.print`) since `PTARLog.lua` stays MQ-free, per its existing design principle. The periodic 1-second `TICK` debug snapshot in the main loop is no longer gated by the old verbose flag — it always fires now, matching "file always gets full debug."
  - Button relabeled "Verbose Debug: ON/OFF" → "MQ Console Echo: ON/OFF"; clicking it now calls `diag:set_echo(...)` and immediately persists the new value via `PTARSettings.save` (DL-003).
- **New module for DL-003, [PTARSettings.lua](../lua/PTAR/PTARSettings.lua):** per-server/character preferences (`last_route`, `echo_enabled`) as plain `key=value` text — deliberately not a Lua-literal table like route files; this data is simple enough that reusing `PTARRouteData.lua`'s literal-only parser would be more machinery than the data warrants. Uses the exact same atomic tmp/bak/promote save pattern `PTARFiles.lua` already uses for the route index, rather than inventing a new persistence mechanism. Lives in `paths.config` — the same folder as routes and the route index (developer confirmed this is the right place, to avoid scattering PTAR-specific files into the shared MacroQuest config root).
- **DL-003 wiring in `PTAR.lua`:** settings are read once at startup, before the first route load — `last_route` pre-seeds the `filename` variable (so the existing "keep filename if still valid in the scanned list, else fall back to the first route" logic in `refresh_routes()` naturally honors it, with no changes needed to that function), and the echo default is `settings.echo_enabled` if present, else `PTARVersion.is_test()`. Settings are saved on every successful route load and every echo-toggle click, always writing both fields together (this file has exactly one writer — the Runner — so there's no partial-update/cross-process race to worry about, unlike route files).
- **Why / evidence:** (b) and (c) are linked because per-line version stamping cannot be trusted while the version string is hardcoded independently in each window title (spec §14 notes both currently read `v0.2.0-test.18` as independent literals — a drift risk). (a) is a new feature, not present in current code. Per-line version stamping is also a **restored requirement**: it was specifically requested previously and silently dropped in an earlier implementation pass — the exact failure mode the decision-log discipline exists to prevent (spec §12).
- **Constraint carried forward:** Development Protocol §9 requires version numbers to follow SemVer. The current literal `v0.2.0-test.18` is already valid SemVer (`MAJOR.MINOR.PATCH-prerelease.identifier`, with `test.18` a legal dot-separated pre-release identifier) — the single authoritative value this decision introduces must preserve that, not just consolidate the duplicate literals.
- **§9's unique-filename requirement — resolved for this project, not literally:** `/lua run PTAR` and every internal `require('PTAR.X')` call resolve to fixed filenames; renaming files per build would require changing the run command and every `require` call each time, which is more complexity than this project's scale warrants (Development Protocol §13). Confirmed with the developer that deployment is a **manual copy** from this repo to the live MacroQuest lua folder — no symlink, no sync script. Given that, §9's actual goal ("make it easy to confirm you're testing the intended version") is satisfied by the single authoritative version value (item c above) shown in the window title and stamped in the log, **paired with a deployment rule, not a code change: always copy the entire `lua/PTAR/` tree plus `lua/PTAR.lua` as one unit for every test build, never individual changed files.** Without that pairing, a bumped version string only proves the entry-point file is current, not that every changed module (e.g. a `PTARRunnerCore.lua`-only change like DL-001) was actually copied — which would produce false confidence, worse than no version number at all. This deployment rule is a process note for the developer, not something enforceable by the code itself.
- **Supersedes:** none.
- **Source:** [PTAR_Rebaseline_Spec.md](PTAR_Rebaseline_Spec.md) §12, §14, §21 (item 2).

### DL-006 — Ignore combat during traversal phases; treat `ground_exit` combat like normal nav

- **Status:** Implemented. This entry decided two things; they carry different evidence and are tracked separately (2026-09-28):
  - **Decision 1 (ignore combat during the 7 traverse/water phases, don't instant-fail): live-verified PASS.** Confirmed twice live, 2026-09-28 (see below) — a related, more serious failure mode was also found and is not yet resolved (see "New finding" below).
  - **Decision 2 (`ground_exit` joins the nav/backtrack/door combat-pause-and-resume group, resuming to `w.exit` specifically): accepted without a dedicated live test — developer's risk-acceptance call, not a claim of equivalent evidence.** Reasoning: the combat-detection entry point is the identical shared code already proven live via ordinary nav combat (e.g. Kylaeris's `Warder NE`/`Warder SE` interrupts, 2026-09-28); the one genuinely distinct piece — the `elseif returning=='ground_exit'` resume branch that targets `w.exit` rather than the waypoint — is covered by two unit tests, both mutation-checked (breaking the pause and breaking the resume branch were each caught, see `runner_core_test.lua`); and `/nav` itself is proven thousands of times over elsewhere. The gap is two already-proven mechanisms composed, not an untested one — unlike DL-007, where the formula looked correct and only real terrain exposed the defect. No live evidence exists for this specific composition; do not describe it as live-verified.
  **SUPERSEDES spec §4** (see Active overrides index above).
- **Existing decision being corrected:** [PTAR_Rebaseline_Spec.md](PTAR_Rebaseline_Spec.md) §4 states as a *confirmed fact*: "Combat interrupts navigation, door interaction, and any traverse phase; 2000ms clear-and-resume delay after combat ends." That is inaccurate on two counts, found via live-log evidence (2026-09-27, see DL-001's evidence log, `PTAR_multiclass_Kateri.log`, `17:31:59`): (1) the code never implemented pause-and-resume for the 7 traverse/water phases — it called `fail()` immediately on combat in three separate places (`traverse_facing`; `traverse_approach`/`traverse_falling`; the four `water_*` phases); (2) `ground_exit`, a real `/nav`-based leg not covered by §4's "traverse phase" wording at all, *also* failed immediately on combat, which was never documented either way.
- **New evidence/reason for review:** Live log: an NPC aggroed during `water_ascend` on a water-drop traversal; the leg immediately failed into `Error`, and the character then took uninterrupted mob damage (HP 100→49 over ~35s in the captured window) plus underwater/environmental damage, with nothing bringing it out of `Error` until manual intervention. Discussed live: the developer confirmed water itself deals damage over time, meaning the prior `fail()`-on-combat behavior for water phases was not just suboptimal but a near-guaranteed death sentence — TAC cannot navigate to a mob in a navmesh gap regardless of what PTAR does, so `fail()` bought nothing protective, only an indefinite exposure window bounded solely by whether the user notices a stalled `Error` status. `ground_exit` is different: it's real navmesh territory (an ordinary `/nav` leg to a captured exit point), so TAC *can* function there — it doesn't share the traversal phases' impossibility and doesn't need the "ignore" treatment.
- **Decision:**
  1. Combat is **ignored** (not acted on) during all 7 traverse/water phases (`traverse_facing`, `traverse_approach`, `traverse_falling`, `water_facing`, `water_descend`, `water_cross`, `water_ascend`). The phase's own logic and timeouts run exactly as if not in combat. This caps exposure at whatever's left of the phase's own timeout budget (seconds, not indefinite), and hands off cleanly to the existing nav-family combat-pause-and-resume logic the moment the character reaches real navmesh again.
  2. `ground_exit` is added to the same pause-2000ms-clear-then-resume group as `nav`/`backtrack`/`door`, since it's an ordinary nav leg where TAC can actually act. Resuming `ground_exit` re-issues `/nav` to the captured exit point specifically (a new `returning=='ground_exit'` branch), since it targets `w.exit`, not the traverse waypoint's own root position — reusing the generic `nav`-resume path (which navigates toward `waypoints[self.index]` itself) would have been wrong here.
  3. §4's "confirmed fact" is corrected by this entry rather than by silently editing the spec document — per the decision-log discipline, the supersession is recorded here and in the Active overrides index rather than requiring the spec file itself to be edited or re-uploaded.
- **Implementation notes:** In [PTARRunnerCore.lua](../lua/PTAR/PTARRunnerCore.lua), the three `if io.combat() then fail(...); return end` lines in the traversal/water phase branches were replaced with a bare `io.combat()` call (kept only so the adapter's existing combat-signal-change logging in `PTAR.lua` still fires during these phases — losing that would be a diagnostic regression, not just a behavior change) plus a one-line comment pointing at this entry. The old standalone `if self.phase=='ground_exit' and io.combat() then fail(...) end` check was removed and folded into the shared `nav`/`backtrack`/`door`/`ground_exit` combat-interrupt condition, with a new `elseif returning=='ground_exit'` branch in the `phase=='combat'` resume logic.
- **Live verification, 2026-09-28 — partial, with a new finding (two-character test, `PTAR_multiclass_Kylaeris.log` and `PTAR_multiclass_Nova(2).log`, Traversal 3 "Drop 3 Water Traversal" [wp_062]).** Test setup: client 1 (Kylaeris) started the traversal, client 2 (Nova) started a few seconds behind. Kylaeris's own traversal had no combat overlap. Nova's did:
  - **The core mechanism this entry decided is confirmed:** combat overlapped Nova's `traverse_falling`, then `water_cross`, then `water_ascend` (`effectiveCombat=true`, XTarget entry `1:56:Auto Hater:NPC`) with **no immediate `fail()`** — the fall completed (`WATER DROP LANDED`), the crossing continued, and the phase's own logic kept running exactly as designed. This is the specific behavior the decision changed, and it held.
  - **New finding, not yet resolved:** the leg still ended in `Error: Water exit stalled at Drop 3 Water Traversal` about 12 seconds into `water_ascend`. Nova's position froze at one point (`-654.49,-2384.60,-988.87`, `navActive=false`) and never moved again for the rest of the window, while `best` (distance to exit) never improved — the stall timeout fired on a real lack of progress, not a logging artifact.
  - **Mechanism (developer: ~99% confidence; not directly confirmed by watching the screen, so recorded as a strong hypothesis, not a fact per Protocol §4):** mob id 56 was the same in both logs, and it was **Kylaeris**, not Nova, who was actually engaging it (at a different location, "Warder Door Loc"). Nova's own `meCombat` stayed `false` almost throughout — the `effectiveCombat=true` reading came from the **group-shared Auto-Hater XTarget slot** (same sharing mechanism already noted in DL-008/TAC source: Auto-Hater aggro is visible to the whole group, not just whoever pulled). TAC's Manual-mode defaults (`Auto-Target Hostiles on XTarget` and `Stick to Target`, both on by default per `reference/TAC` v3.1) would try to move the character toward any hostile on XTarget — including one it never pulled — via `/stick` or its off-mesh fallback keys, which do not require a navmesh path. If that fired here, it would have directly fought PTAR's own held vertical/forward keys during the ascend, explaining the frozen position and the eventual stall.
  - **This means DL-006's own reasoning had a gap:** the entry's "why" argued TAC "cannot navigate to a mob in a navmesh gap regardless of what PTAR does," so ignoring combat costs nothing extra. That's true of `/nav` specifically, but this finding suggests TAC's Manual-mode `Stick`/off-mesh-fallback path is not blocked by the lack of a navmesh, and can compete with PTAR's manual movement during a traversal. Ignoring combat is still clearly better than the pre-fix instant-fail (no immediate `Error`, the fall/crossing still completed, and this failure mode is not death-adjacent the way the original water-damage incident was) — but it does not fully insulate a traversal from TAC-driven interference when combat is present nearby, even combat the character isn't personally engaged in.
  - **Path to confirming the mechanism:** [DL-013](#dl-013--route-authored-tac-pauserun-events-explicit-opt-in-verified-through-ac-status)'s route-authored TAC pause/run events give a direct test once live-verified — pausing TAC before a traversal chain should prevent this interference if the hypothesis is right, and the developer noted this is how it'll actually get confirmed, rather than a separate reproduction attempt.
  - **`ground_exit` combat-pause-and-resume:** not exercised in this test (neither character reached a `ground_exit` combat interruption); still pending live verification.
  - Until the mechanism is confirmed (via DL-013 or a direct observation), do not describe DL-006 as fully validated beyond: instant-fail-on-combat during traversal phases is gone (confirmed), and a stall can still occur under group-shared combat via a mechanism not yet directly observed (Development Protocol §10).
- **Supersedes:** [PTAR_Rebaseline_Spec.md](PTAR_Rebaseline_Spec.md) §4's "any traverse phase" combat-interrupt claim, and its silence on `ground_exit`.

### DL-007 — "Fall approach passed limit" failure: the 2D distance formula, not the capture, is wrong

- **Status:** Implemented, **live-verified PASS, 2026-09-28.** Margin resolved via reasoned estimate + explicit developer sign-off rather than a precise field measurement (see below) — acceptable per Development Protocol §15 since it followed the evidence-and-discussion process, not a guess.
- **Live verification (2026-09-28), two independent characters, both through the actual incident waypoint `wp_060` ("Drop 1 Water Traverse"):**
  - **Kylaeris**, build `0.2.0-test.22`, `PTAR_multiclass_Kylaeris.log`: `FALL TRAVERSE Drop 1 Water Traverse [wp_060] ... origin 619.87,-2234.97,-443.62; max approach 148.2 units / 7000 ms`, then `GROUND DROP FALL START ... descent speed 27.5 Z/s`, then `WATER DROP LANDED Drop 1 Water Traverse descent 265.0 Z`. No approach-limit error.
  - **Nova**, build `0.2.0-test.23`, `PTAR_multiclass_Nova(1).log`: same waypoint, `max approach 148.2 units / 7000 ms`, `descent speed 29.4 Z/s`, `WATER DROP LANDED Drop 1 Water Traverse descent 264.2 Z`. No approach-limit error.
  - Both runs computed the same 148.2-unit limit (matching `dist(w, w.ledge)+45` on this waypoint's real geometry), cleared the approach that previously failed at 113.2 units, and completed the fall/landing cleanly. Two independent characters, two clean runs — this closes the "Pending Live Verification" entry for DL-007 in the project ledger.
- **Correction to this entry's own history:** the first pass at this investigation concluded the waypoint's `ledge` capture was imprecise and recommended recapturing it. **The developer confirmed the capture is accurate** — reaching the ledge genuinely requires walking up a real incline, and the recorded ledge point is where the true edge is. That recapture recommendation was wrong and is retracted; recorded here rather than silently deleted, per the decision-log discipline (§2).
- **Incident:** `18:03:46.354`, log `PTAR_multiclass_Kateri.log`: `Error: Fall approach passed 113.2-unit limit at Drop 1 Water Traverse` (waypoint `wp_060`, route `PTAR_SleepersTombKera.lua`).
- **Confirmed data (developer-provided, matches route file):** departure `wp_060 = (619.659, -2236.979, -444.873)`; `ledge = (617.781, -2335.123, -412.873)` — a **32-unit climb** over a 2D distance of ~98.15 units, confirmed to be a real incline, accurately captured.
- **Root cause, revised:** `approach_limit = max(35, xy(w, w.ledge) + 15)` in [PTARRunnerCore.lua](../lua/PTAR/PTARRunnerCore.lua) uses `xy()`, which **discards the Z axis entirely** — it computes the same "distance" for this 32-unit climb as it would for a perfectly flat 98.15-unit walk. That's a formula defect, not a capture defect: any traverse with elevation change will have its approach budget systematically undercounted.
- **A second, independent shortfall found in the same data:** log telemetry shows the character had already traveled ~113.6 units from the origin (crossing the limit) while still not visibly falling — roughly **14 units past the ledge's own recorded position** (straight-line origin-to-ledge is ~99.8). So even a correct 3D-distance calculation (≈103.2, giving a ~118.2 limit) would likely still have been too tight. This suggests the true physical drop-off is somewhat past the visually-captured edge point itself — plausibly an engine/collision characteristic (solid ground often extends slightly past a visual edge) rather than anything wrong with the capture.
- **Resolving the open question (no exact field measurement available):** the developer couldn't get a precise measured distance past the ledge (log resolution and live testing both fell short of pinning down an exact number). Instead, a scale reference was established: a screenshot of an unrelated Bazaar location, where "10 units" was confirmed to be roughly the distance from a pedestal to a nearby doorway — a short, room-scale distance, not a large one. Against that scale, the old `+15` margin was already only "about 1.5 doorways" of slack, and the observed ~14-unit overshoot past the ledge (see above) was comparable in size to the *entire* old margin — meaning the real shortfall is on the same order of magnitude as the whole existing buffer, not a small fraction of it. Given that, `+45` (roughly 3x the old margin, "4-5 doorways") was proposed as a reasoned, still-bounded estimate — not a measured value, but a deliberate, discussed one. **The developer explicitly approved 45 as a starting point, to be adjusted from real-world usage going forward** rather than held as a final, precisely-derived number.
- **Decision:** (1) switch the formula from 2D `xy(w, w.ledge)` to full 3D `dist(w, w.ledge)`, so elevation change is no longer silently dropped; (2) raise the flat margin from `15` to `45`; (3) the live comparison (`dist(p, self.traverse_origin)` vs. the limit) was also switched from `xy()` to `dist()` for consistency — the limit and the thing it's compared against must use the same distance metric, or the fix would only be internally consistent on paper.
- **Implementation:** [PTARRunnerCore.lua](../lua/PTAR/PTARRunnerCore.lua) — both the `FALL TRAVERSE` log-line computation and the `traverse_approach` limit check now use `dist(w, w.ledge)+45` and `dist(p, self.traverse_origin)` respectively, replacing the prior `xy(...)+15` pair.
- **Explicitly acknowledged as not fully evidence-derived:** `45` is a reasoned estimate, not a measured value — flagged here so it isn't later mistaken for a precisely-derived constant. If it proves insufficient or excessive on other traverses (especially ones with a different incline profile than `wp_060`), that's new evidence for a future revision, not a sign this decision was made carelessly.
- **Supersedes:** none (this entry supersedes its own earlier conclusion, not a spec item).
- **Source:** Live log evidence (`PTAR_multiclass_Kateri.log`, 2026-09-27) + `PTAR_SleepersTombKera.lua` route data (`wp_060`) + developer discussion and confirmation.

### DL-008 — Multi-character door coordination via group chat (primary/secondary roles)

- **Status:** Implemented, pending live verification. **Not derived from the spec** — this is new functionality identified through live discussion of a real multi-boxing failure mode, not a spec-required fix.
- **The problem:** the developer runs a group across 3 physically separate machines (one desktop, two laptops), using TAC's Assist+Chase for followers everywhere except traversal segments (chase-follow can't cross a navmesh gap, same reason PTAR's own traversal phases exist). Running PTAR independently on every character was considered and rejected because of a confirmed, reproduced failure mode: two independent PTAR instances have zero coordination, so if two characters reach the same door within a few hundred ms of each other, character B's `door_state()` poll can still read "closed" (the open state hasn't propagated/settled yet) right after character A already opened it — B then clicks the same door again. Many EQ doors are toggles, so B's click swings it back closed. Both legs then stall/fail, backtrack to the same spot in front of the door, and repeat indefinitely (confirmed by the developer as an actually-observed, reproducible loop, not a hypothetical).
- **Why the fix works:** the underlying constraint is that a shared, mutable game object (the door) is being independently mutated by processes with no shared state. Fixing it requires either (a) real cross-machine coordination so only one character ever clicks, or (b) accepting the risk. A shared local file (as used elsewhere in this project for atomic state, e.g. `PTARSettings.lua`) was considered first but doesn't work — the 3 machines share no common filesystem. MacroQuest's native Lua Actors/mailbox system (`require('actors')`) was researched and confirmed **single-machine only** per official docs — not viable either. The chosen mechanism instead reuses a channel that is already inherently cross-machine: EverQuest's own group chat, which the server relays to every group member regardless of which PC they're on, combined with MacroQuest's Lua `mq.event()`/`mq.doevents()` chat-pattern-matching system. No new plugin or dependency required.
- **Empirically verified before implementing (Development Protocol §4 — external system behavior, not guessed at):** the developer ran a small throwaway diagnostic script (`mq.event` with a catch-all `'#*#'` pattern) and confirmed the exact raw text MacroQuest's event matcher sees for another character's group-chat line is `"<Name> tells the group, 'message'"` — matching the well-established, long-standing EQ client format used across the wider EQ tooling ecosystem. Also observed: the event fires **3 times** for a single chat line (cause unknown, not investigated further) — the implementation is written to be idempotent to this rather than assuming exactly one firing.
- **Decision — scope, confirmed explicitly with the developer:** only the shared door-phase branch that already covers **both** `door_after=='continue'` and `door_after=='finish_open'` gets the primary/secondary treatment (these two outcomes were already handled by identical code in `PTARRunnerCore.lua` before this change — the distinction between them happens later, inside `advance()`). The `finish_zone` branch is **untouched** — every character, primary or secondary, still clicks its own door and waits for its own zone transition, since zoning is inherently per-client; there is no such thing as zoning by proxy.
- **Design choices made and confirmed with the developer:**
  1. New `door_role` setting (`primary`/`secondary`), persisted per-character like the existing settings, **defaulting to `primary`** — so a solo character with no one else around behaves exactly like before this change, with zero opt-in required. Only followers explicitly switch to `secondary`.
  2. Role is exposed as a live-queried adapter function `io.door_role()`, not baked into the runner at construction time — a UI toggle change takes effect immediately without needing to reload the route, consistent with how every other MQ/settings-dependent fact in this codebase is already read (`io.combat()`, `io.mesh()`, etc.) rather than introducing a new, inconsistent mechanism.
  3. Tagged message format `PTAR:DOOR:<door_id>:OPEN` sent via `/g` — terse and unambiguous, can't be confused with real chat, trivial to parse.
  4. Primary broadcasts **only** on a definitively-confirmed `state==true` — it does **not** broadcast during the existing "door state unavailable for 2000ms, proceed anyway" stall fallback, since primary doesn't actually know the door is open in that case either. A secondary relying on confirmation that never arrives will time out and fail on its own, which is the correct outcome (primary's own uncertainty shouldn't manufacture false confidence downstream). Confirmed with the developer as an intentional judgment call, not an oversight.
  5. Secondary **never clicks, under any circumstance** — including after its own wait times out. A "click anyway as a fallback" path would just reintroduce the exact race being eliminated. A timed-out secondary fails the leg exactly like any other stall (Error, Resume/Stop), matching how every other bounded wait in this system already behaves.
  6. Secondary's wait-for-confirmation timeout reuses the existing 8000ms door-click-wait constant, purely for consistency. **Explicitly flagged as an unverified implementation choice, not a measured value** — a secondary traveling a longer distance to the same door than the primary may legitimately need more time than that. Revisit only with evidence of an actual premature timeout, per the Development Protocol §15 standard, same as DL-007's margin.
- **Implementation:** [PTARSettings.lua](../lua/PTAR/PTARSettings.lua) — `door_role` field added alongside `last_route`/`echo_enabled`. [PTAR.lua](../lua/PTAR.lua) — `door_role`/`confirmed_doors` state, `mq.event('ptar_door_open', "#1# tells the group, '#2#'", ...)` registered once at startup, `mq.doevents()` added to the main loop, three new adapter functions (`door_role`, `door_confirmed`, `announce_door_open`), a `save_settings()` helper (all three settings must be written together each time, since `PTARSettings.save` does a full overwrite, not a partial merge — every existing call site was updated to go through it rather than passing a partial table), and a new "Door Role: Primary/Secondary" UI toggle. [PTARRunnerCore.lua](../lua/PTAR/PTARRunnerCore.lua) — the shared `continue`/`finish_open` door-phase branch now checks `io.door_confirmed()` alongside `state==true`, broadcasts only when primary and freshly confirmed, and secondaries skip the click block entirely in favor of a bounded wait-or-fail.
- **Status update — Live-verified, PASS, 2026-09-27.** Two-character test confirmed both directions of the race (secondary arriving at a door first and waiting; secondary catching up after primary already opened it), and the untouched `finish_zone` path still worked correctly for both roles. One benign observation: a lag hiccup let the secondary briefly get ahead of the primary at one door — developer confirmed this caused no problem, the secondary still proceeded to the door and zoned correctly. Not a defect, no action needed.
- **Supersedes:** none.
- **Source:** Live discussion and reproduced failure report, 2026-09-27; MacroQuest documentation research ([Lua Actors](https://docs.macroquest.org/lua/actors/), [Lua Events and Binds](https://docs.macroquest.org/lua/events-and-binds/)); developer-run empirical verification of the raw chat-line format; live two-character verification test, 2026-09-27.

### DL-009 — Levitate breaks ground-drop traversal fall-detection (known limitation, deferred)

- **Status:** Confirmed, root cause understood, **deliberately not fixed now** — developer's call: technically possible but "messy." Documented as a known limitation instead.
- **Incident:** During the DL-008 live test, neither of two characters could complete "Drop 1 Water Traverse" while both had an active Levitate buff. Removing the buff allowed successful traversal of the next ground drop immediately after.
- **Root cause:** [PTARRunnerCore.lua](../lua/PTAR/PTARRunnerCore.lua)'s ground-drop fall detection is purely speed-based (spec §4: descent `>15 Z/s` signals a fall has begun). Levitate prevents that kind of physics-driven fall entirely — walking off a ledge while levitating continues roughly level, or descends only under direct player control, never crossing the 15 Z/s threshold. `traverse_approach` then times out after 7000ms with "Fall did not begin," which is exactly what was observed. This is not a bug in the detection logic; it's an unstated precondition (the character must not be levitating) that the entire ground-drop mechanism silently assumes.
- **Decision:** do not add active Levitate detection/pre-check now. Documented here as a known limitation: **characters must not have Levitate active before a fall-based traversal waypoint.** Revisit if this becomes a recurring practical problem — the developer's own assessment is that detecting and handling it cleanly is "possible but messy" (Levitate can be a buff, a spell effect, or item-granted, with no single simple check covering all sources cleanly; graceful handling would also need to decide what to do about it — refuse the waypoint outright, prompt the user, or something else — which is exactly the kind of design conversation to have if/when this actually recurs, not preemptively).
- **Supersedes:** none.
- **Source:** Live two-character test, 2026-09-27.

### DL-010 — Multi-client waypoint barrier sync: agreed design, implementation deliberately held

- **Status:** Live-verified end to end, build `0.2.0-test.25`. Core barrier mechanism, requirement #3, `Group.Member` self-exclusion, and the chat-ordering assumption (checked, not contradicted) — see below. Item 5 (primary-drops gap) is reclassified as intended v1.0 behavior, deferred to a post-1.0 feature release (developer decision, 2026-09-29). The barrier-timeout-then-proceed path is opportunistic-only, no dedicated test warranted.
- **The problem being solved:** discovered during the DL-008 live test — with every client running PTAR for the full route (see below), a client that gets far enough ahead of the others can pull/aggro mobs alone, triggering its own independent combat-pause while the others keep moving, widening the gap further; expected to compound as client count increases.
- **Key context clarified during discussion, correcting an earlier assumption:** TAC's Assist-Chase mode uses `/nav` internally to follow the main assist, which cannot function through a navmesh gap at all — so Chase was never viable for the *whole* route, not just the traversal segments. The actual intended model is: **every client runs PTAR for the entire route, continuously, with TAC left in Manual (fight-only, no movement) throughout.** This makes waypoint drift a full-route concern, not a narrow traversal-adjacent one.
- **Design considered and rejected: primary-announces/secondary-waits (the door pattern) applied to every waypoint.** This enforces ordering (no one skips a checkpoint out of sequence) but not a distance bound — the primary is never itself throttled, so it can still drift arbitrarily far ahead over time if it simply has better luck avoiding combat. Rejected because it doesn't actually solve the motivating problem.
- **Agreed design: full barrier sync at every waypoint.** Every participating client waits at each waypoint until *every other currently-tracked participant* has also confirmed reaching it, before any of them proceed. This bounds drift to at most one waypoint between any two clients, for any number of clients, by construction. Explicit tradeoff accepted: the whole group now moves at the pace of whichever client is currently slowest, gated point by point — a noticeably more lockstep feel than chase-follow ever had. Developer confirmed this is the desired tradeoff ("the safest thing would be...").
- **Roster membership — two criteria, both required, confirmed with the developer:**
  1. **Currently in my live group** (`mq.TLO.Group.Member(i).Name()` / `.Members()`, confirmed to work cross-zone). Leaving the group drops a participant from the wait-set **instantly** — no timeout needed for a genuine disconnect, since EQ itself removes a disconnected character from the group automatically.
  2. **Has recently sent a `PTAR:HERE` heartbeat.** Group membership alone isn't sufficient — a real duo partner or a character chase-following without PTAR loaded would show up in the group roster but never confirm anything, hanging the barrier forever. The heartbeat/bark is the signal that a group member is *actually running PTAR on this route*, independent of group membership. Losing the heartbeat (script crashed or froze without the character actually leaving the group) drops the participant via timeout, since group membership alone wouldn't catch that case.
  - **`PTAR:HERE` carries no progress/waypoint/door information at all** — confirmed explicitly with the developer. Its only job is roster liveness; it is never conflated with `PTAR:WAYPOINT:<id>:REACHED` or `PTAR:DOOR:<id>:OPEN`.
- **`door_role` scope — narrower than it might first appear, confirmed explicitly:** it continues to govern *only* who clicks a `continue`/`finish_open` door, exactly as shipped in DL-008. The new barrier-wait applies symmetrically to every participant regardless of `door_role` — there is no "primary" for waypoint sync, only for door-clicking. The "Door Role" UI button will likely need relabeling when this is implemented, so it doesn't read as if it also governs waypoint sync.
- **Second risk identified during this discussion, relevant to any design where one client can get far ahead:** `confirmed_doors` entries (from DL-008) never expire. If a primary opens and announces a door long before a lagging secondary arrives, and that door can auto-close/reset/be closed by something else in the interim, the secondary would trust a stale confirmation and stall with no click-fallback (secondaries never click, by design). Not yet addressed — noted here so it isn't lost once implementation resumes.
- **Starting timing values — explicitly flagged as first-guess estimates, not measured, per the Development Protocol §15 standard used for every other timing constant this session:**
  - Bark heartbeat interval: **5000ms.**
  - Roster expiry (heartbeat silence): **15000ms** (3 missed heartbeats) — enough slack to tolerate one or two delayed/dropped messages without a false removal.
  - Barrier-wait timeout: **120000ms.** Deliberately set *above* the existing ~90000ms ceiling on a single normal-nav-leg's own travel-stall timeout — a shorter barrier timeout risked abandoning a participant who hadn't even hit their own individual failure condition yet, which would defeat the sync's purpose.
- **Traversal barrier-gating — resolved: both sides, sync.** Traversal is exactly where TAC can't help and where drift is most dangerous, and a barrier is needed on **both** the departure side (don't let anyone begin the irreversible fall/swim until everyone's gathered) and the exit side (don't let anyone continue past the traversal until everyone's confirmed completion) — reasoning below.
- **Departure-side collision risk identified and resolved.** A traverse waypoint's own "reached" radius is intentionally tight (spec: defaults to 3, capped at 5). Barrier-syncing everyone to converge on that exact point simultaneously (illustrated vividly: "imagine 6 ogres in a party, all trying to reach the departure point") creates a real physical-collision risk that could disrupt heading verification or the `traverse_origin` capture. Resolved with:
  - **Alphabetical turn order** (or any equally deterministic roster-derived ordering, e.g. group slot number) — every client computes the same order independently, no negotiation needed over chat.
  - **One "cleared" signal per client** (`PTAR:WAYPOINT:<id>:CLEARED` or similar), sent when that client enters the actual fall/dive (`traverse_falling` or the water equivalent) — **not** a granular per-phase broadcast. A 4-stages-per-client pipelining idea was considered and rejected: "started the next stage" doesn't reliably mean "physically vacated the collision zone" (e.g., `traverse_facing`→`traverse_approach` fires the instant heading verifies, while the character is still standing at the departure point) — so gating on stage-start rather than actual physical clearance would still leave a real collision window, while costing 4x the chat traffic and state-tracking of the simpler single-signal design.
  - **Bounded wait, not indefinite block, for the next-in-order client**, matched to the *predecessor's own worst-case time to fail or succeed* on that traversal type (e.g. ground: `traverse_approach` 7000ms + `traverse_falling` 20000ms = 27000ms). This deliberately reuses the project's existing bounded-wait-then-proceed philosophy (already used for combat, doors, nav stalls) rather than trying to enumerate every possible way a predecessor could get stuck — the developer raised wanting to "future-proof... situations I haven't thought of," and the answer is that the existing generic philosophy already covers unknown-shaped failures, without needing to special-case them.
  - **Waiting clients gather in a loose "vicinity" radius** (tight departure radius + a fixed buffer), not the exact tight spot — **derived automatically from the traverse waypoint's own existing captured data, not authored.** An explicit route-author-placed "staging waypoint" was considered and rejected: hard to guarantee every traversal has one, and doesn't help if placed too close anyway. The automatic vicinity radius gets the same effect with zero authoring burden, on every traversal in every route.
  - **A "conga-line" idea (computing precise queue-slot coordinates and issuing each waiting client a `/nav` to a mathematically-derived position) was proposed and explicitly rejected** after direct pushback: a computed coordinate is never verified against real terrain the way every other position in this project is (hand-captured, by design — spec explicitly scopes out automatic route generation). DL-007 already showed that even a *hand-captured, physically-verified* point needed a real-world correction because straight-line distance math didn't match actual terrain; a fully synthetic, never-verified coordinate is strictly less trustworthy than the thing that already caused a live failure once. Also unnecessary: exact-position precision is only needed for whichever *one* client is currently taking its turn, not for everyone idly waiting.
  - **Confirmed explicitly: waiting clients still walk back to the exact captured departure point before beginning their own facing/fall attempt** — the loose vicinity radius is purely a waiting area, never a new starting point for the actual attempt. This was the key point that resolved a related concern (does waiting off-point reopen DL-007's distance-budget math for a whole radius of possible starting points instead of one fixed point?) — it doesn't, because `traverse_origin` is still captured at essentially the same precise point it always has been, regardless of where a client was standing moments earlier.
- **Exit-side: plain barrier-wait, no turn-based choreography — accepted without added complexity.** Exit points have their own radius too (also author-chosen, same collision risk *could* apply), but since clients depart the traversal one at a time (per the departure-side ordering above), they'll tend to *arrive* at the exit staggered too, inheriting some natural spacing for free. Not a guarantee — crossing-time variance could still produce near-simultaneous exit arrivals — but the developer explicitly chose not to add speculative machinery for a problem with no evidence yet ("I don't want to engineer for problems that might not exist in reality"), consistent with Development Protocol §13. Revisit only if real exit-side collision is observed.
- **Amendments, 2026-09-28 (review of the entry before implementation; developer decisions unless marked otherwise):**
  1. **Message names:** the waypoint barrier message is `PTAR:WAYPOINT:<id>:REACHED` (developer: unambiguous, and easier for bug tracking). The departure-side signal keeps the same prefix, `PTAR:WAYPOINT:<id>:CLEARED`. *The developer confirmed `REACHED`; the `CLEARED` spelling is recorded as an implementation choice consistent with it and can be changed freely before implementation.*
  2. **Vicinity buffer value** (departure-side waiting radius beyond the tight radius) and the **water-traversal equivalent of the predecessor wait** (only the ground figure, 7000 + 20000 = 27000 ms, was derived above): both are **implementation choices**, to be picked at implementation time and flagged there as unmeasured estimates under Protocol §15.
  3. **`confirmed_doors` staleness — resolved (supersedes the "Not yet addressed" bullet above).** Code read on 2026-09-28: entries in `PTAR.lua` are keyed by door ID only and are never cleared anywhere (not on Start, Stop, route change or zone change), so they persist across runs and across zones (door IDs are per-zone). Two problems: cross-run staleness (every door reads "confirmed" on a second run) and in-run staleness (door closes after the primary announced it). **Decision:** a door waypoint is an ordinary waypoint, so the DL-010 barrier gates it. The barrier must sit **between reaching the door waypoint and starting the door phase**, so the primary clicks only once everyone has gathered; and when that barrier releases, each client **clears that door's confirmation** and waits for a fresh `PTAR:DOOR:<id>:OPEN`. This covers both problems without a timer. **Unverified assumption (Protocol §4):** the server relays group chat in the order sent, so every client sees all `REACHED` barks before the primary's `OPEN`. Check receipt order in the first live multi-client log; do not describe it as confirmed until then.
     - **Rejected: secondary opens the door if it finds it closed, with alphabetical priority.** It reintroduces secondary clicking, which DL-008 decision #5 rejected; ordering narrows the two-clickers race but does not close it, since it needs each client to have seen the other's bark first.
     - **Rejected: one-shot confirmations (delete on use).** After a backtrack a secondary re-enters the same door phase while the primary does not re-announce, so it would strand.
     - **Rejected: timestamp expiry.** Adds a guessed timing value and depends on how fast a secondary's own door-state read reflects reality, which is unmeasured.
     - **Related path noted:** the nav-stall fallback (`io.door(previous)` in `PTARRunnerCore.lua`, nav phase) is not role-gated; the adapter only clicks when the door does not read as open, so it is guarded, but a client advancing on a stale confirmation could still reach it. The clear-on-release rule removes that entry route.
  4. **No door-specific gather radius.** Real route data (`PTAR_SleepersTombKera.lua`, `PTAR_EasternWastestoSleepersTomb.lua`, read 2026-09-28): all 11 door waypoints are preceded by a normal waypoint; in 10 of 11 it is at the identical position (0.0 units), in the other 2.5 units. Door waypoints sit 31.5–34.0 units from the door in 8 of 9 Kera doors (5.9 for the Warder door; 7.4 and 17.6 in Eastern Wastes), all with the default radius of 15. A door waypoint is where the author stood, not the door's own position, so a closed door does not make it unreachable, and the barrier gathers clients at that stand-off point with the ordinary radius. The developer's initial 30-unit idea was dropped as unnecessary; a larger radius would also move the point where PTAR stops walking and thus the door click position, whose maximum working range is **not measured** (only an inference that ~33 ± 15 units works in that route). The pre-door normal waypoint is an authoring convention observed in these routes, **not** something the design relies on.
  5. **Open item, not designed:** `door_role` is a manual setting, and DL-010's roster drops a client that leaves the group or stops sending heartbeats. If the character set as primary drops, nobody is left to click doors, and secondaries time out at the first door. The DL-008 live test included a server outage, so this is plausible, not hypothetical. A possible direction (deriving the clicker from the roster, e.g. first alphabetically) would supersede part of DL-008 and needs its own discussion; nothing is decided.
  6. **Barrier release stays local to each client; an explicit broadcast "everyone's here, proceed" (GO) message is NOT adopted (developer, after discussion).** Concern raised: a client that miscounts might proceed without sending its `REACHED` and strand the others. Resolved by two rules, both agreed:
     - **Bark on arrival, unconditionally.** A client sends `PTAR:WAYPOINT:<id>:REACHED` the moment it reaches the waypoint, *before* evaluating the barrier; the barrier only decides when that client leaves. A miscounting client therefore never withholds its bark: undercounting only lets that one client run ahead (bounded), overcounting only makes it wait alone until timeout. Neither stalls anyone else. The stall scenario is only possible if the bark were sent on release, which this rule forbids.
     - **Count names, never messages.** Barrier state is a set of sender names per waypoint ID, complete when every name in the current roster is present. A counter would be wrong because each group-chat line fires the event three times (DL-008).
     - **Log every release** with the roster expected and the names seen, e.g. `released <id>: expected [A,B,C], seen [A,B,C]`, so a miscount is visible in the log.
     - **Why not GO:** a client that never sends `REACHED` stalls whoever is counting under either design (the leader under GO, every client under local release), so GO does not protect against it; it needs a sender (a fixed primary reopens the item-5 gap; a roster-derived one can double-send) plus a local fallback anyway; and a sender's miscount would release everyone early instead of only itself. **Revisit only if live logs show lost or missed `REACHED` messages**, in which case GO would be added as a repair layered on local release, accepted only while a client is waiting at that waypoint (to avoid the `confirmed_doors` staleness problem).
  7. **Still open, not decided (raised 2026-09-28):** (a) what the barrier does when its timeout expires: proceed without the straggler (which stays in the roster on its live heartbeat and would stall the next barrier unless marked excluded until it catches up) or fail the leg to Error; (b) whether the departure-side signal is renamed from `CLEARED` to `DEPARTED` (it means "I am in the fall", and `CLEARED` could be misread as a release); (c) whether `REACHED` is re-sent periodically while a client waits at a barrier, to cover a client that starts late and would otherwise miss earlier barks; and the related question of when barrier state is cleared (never clearing lets a second run pass every waypoint instantly; clearing at Start discards earlier barks).

### DL-012 — Test harness design: Lester (vendored) + custom runner with per-file subprocess isolation

- **Status:** Agreed 2026-09-28 (tooling and design). **Implemented** in commit `27926a6` (80 tests, local/simulated validation only; see "Implementation status" below). The developer delegated remaining detail (discovery, CI contract, timeouts, coverage) to the implementer. Still open: luacheck and CI on push (separate topics). (Earlier status "implementation pending" corrected on 2026-09-28.)
- **Decision:**
  - **Framework:** [Lester](https://github.com/edubart/lester) v0.1.5, vendored at `test/vendor/lester.lua` (MIT notice embedded; SHA-256 `a6744c47…d2adb0`; byte-identical to upstream master when fetched). Chosen over busted (its `luasystem` dependency compiles C; no compiler on the dev machine), u-test, and a hand-rolled layer.
  - **Runner:** custom Lua script run under `luajit`; one subprocess per `test/*_test.lua` file. Support code lives in `test/harness/` and `test/vendor/`. Tests live outside `lua/` because everything under `lua/` ships.
  - **Real modules under test**, loaded with `require` and `lua/?.lua` on `package.path`. Fakes only at existing seams: RunnerCore's `io`, Combat's `mq` parameter, temp dirs for file modules. `PTAR.lua` and `PTAREditor.lua` are parse-check only.
  - **Exit codes:** 0 pass, 10 tests failed, 11 load error. Anything else (notably 1) means a crash or launch failure. Lester's own `exit()` is not used.
  - **Guards:** fail on zero test files, a file registering zero tests, or zero tests run (Lester's `report()` returns success on zero tests). Skips require a reason, print every run and are counted separately, never as "ran". Sorted file order; tests kept in arrays.
  - **Helpers:** `on_cleanup` (LIFO, per test, even on failure), `patch`, `with_temp_dir` (refuses any path outside %TEMP% or an existing dir; never touches repo `config/PTAR/` or MQ folders), `fresh_require` (clears all `PTAR.*`), `assert_contains` (plain substring), `near` (floats). No bare `assert(x)`.
  - **Launch quoting:** all launches go through one function that wraps the command in outer quotes (documented `cmd /c` behavior for paths with spaces). **Verified locally 2026-09-28:** with both interpreter and script paths quoted and containing a space, the launch fails without the wrapper and succeeds with it.
- **Implementation status (2026-09-28):** built in `test/harness/` (`run.lua`, `bootstrap.lua`, `t.lua`, `fs.lua`, `sim.lua`, `syntax_check.lua`) plus `test/check.cmd`. Suites: `runner_test.lua` and `harness_test.lua` (the tooling itself), `route_data_test.lua` (spec l26–l64), `runner_core_test.lua` (DL-001, DL-006, DL-007, DL-008). Local/simulated validation only; each suite was mutation-checked by breaking the production condition and confirming the matching tests fail. Two bugs found by running: the runner reported a load error as a guard failure (fixed), and one wrong test expectation (fixed); one `RouteData` mutation (identifier check) initially slipped through and a test was added. Not covered by a mutation check: DL-008's "primary with unavailable door state does not announce" (no production line to break without adding behavior). Behavior with no spec/DL source and therefore no assertion: `RouteData.create` duplicate-capture window, 3-decimal position rounding, the 4 MiB read cap, nesting-depth limits.
- **Guardrails so tests validate behavior rather than dictate it** (Protocol §5, §7):

### DL-013 — Route-authored TAC pause/run events (explicit opt-in), verified through `/ac status`

- **Status:** Design **agreed** 2026-09-28, developer-approved item by item. Implemented in five steps, build `0.2.0-test.23`. **Live-verified, 2026-09-28** (see below) — the core mechanism is confirmed; the graying/layout of the UI itself was not specifically checked. **SUPERSEDES the "PTAR does not manage TAC" boundary in [PTAR_Rebaseline_Spec.md](PTAR_Rebaseline_Spec.md) §3 and §15** (see Active overrides index).
- **Decision:** a route author may put two optional fields on any waypoint, `tac_before` and `tac_after`, each `'pause'` or `'run'`. PTAR then sends `/ac pause` or `/ac run` and verifies the result. Purpose: give the author control over when TAC controls movement and when PTAR does, e.g. pause TAC for a whole traversal chain including the navmeshed sections between drops, so PTAR has total control there. Nothing else about TAC is managed; the Editor still never calls TAC.
- **Why / evidence:**
  - **Model:** every client runs Manual and PTAR runs the whole route (developer's preference: TAC and PTAR should not fight over movement). The hybrid (followers on Chase for normal legs, PTAR only in chains) was considered and **rejected**; it would need a "PTAR acts only inside chains" concept far larger than the events. Developer-stated facts behind it: Chase cannot cross a navmesh break, does not error or pause, and resumes when a path to the Main Assist exists again; Sleeper's Tomb has navmeshed hallways between its three drops; buffbots and undergeared alts stay at the entrance and never run PTAR; typical run is 2–3 combat characters.
  - **TAC source, v3.1 (`reference/TAC`, read 2026-09-28):** Manual is not movement-free by default (`manual_stick`/`manual_auto_xtarget` default true, so an engaged mob draws the character toward it, `triune.lua:22250`); TAC issues movement stops before any cast in every mode (`stopMovementForCast`, `triune.lua:2347`); `/ac pause` sets `ctrl.running=false`, which also turns off attack/autofire and halts movement (`triune.lua:21804`), while the plugin loop keeps ticking (`pluginManager.tick()` is not gated on `ctrl.running`); `ctrl.running` is not persisted (`triune.lua:6250`, "never auto-start on load"), unlike `/ac chase on|off`, which is saved to the loadout; `/ac status` prints `status: running|paused, mode: <mode> (<submode>), burn: ON|OFF` only. **No TAC interference with a PTAR traversal has been observed in any live log** (the traversal failures on record, DL-006/007/009, were not TAC movement); these events are protection against interactions found by reading source, chosen by the developer as worth the scope.
  - **Verification precedent:** PTDeathRecovery already catches TAC console output with `mq.event('...[Triune] status: #1#, mode: #2#, burn: #3#...')`, treats a command acknowledgement as not proof, queries `/ac status` first and verifies after, ignores status lines that arrive with no query active, and retries a bounded number of times. PTAR takes the **shape** from it, not its code or its numbers (Protocol §15); PTDR's readiness/canary machinery (for slow TAC after a zone change) is deliberately not adopted.
  - **Working preference (developer):** lean toward automation where the developer judges the risk small; a death is low-cost in PT (14-hour lockout blocks creating a *new* non-respawning instance only, re-entry is allowed, so a wipe means re-entering); the developer, not Claude, makes that judgment per decision. Log everything.
- **Shape:** absent field = **no event, the default**. A route with no events produces zero TAC commands and zero TAC queries and behaves exactly as today (requirement test). No standalone event entries: they would need a position or would duplicate before/after, and every waypoint assumption (x/y/z, `wp_###` IDs, `last_good`, backtrack, nearest) would need special cases. `format_version` **stays 3**: existing routes stay valid; a stale build on another PC would ignore events silently, which is today's behavior and is visible through the build stamp in its log.
- **Timing:** `tac_before` fires on arrival, before the waypoint's own action (before the facing/fall starts; before a door phase). `tac_after` fires when the waypoint's action completes, at the top of `advance()`, before its terminal cases (so `run` on a finish waypoint fires before "Completed"; on a traversal, after the exit is verified).
- **State semantics:** events are markers with state meaning: the effective TAC state at a waypoint is the last event at or before it; **before any event the state is undefined and PTAR asserts nothing** (no assumed "run"). On Start, Resume/Use-Nearest and backtrack PTAR asserts the effective state through the same machine, only when an event exists at or before that point. Commands are check-first and idempotent so retries, backtracks and mid-route starts are safe.
- **Machine (runner, two new phases `tac_before` and `tac_after`, driven only through `io`):** query `/ac status` (wait for the answer) → already the goal state: do nothing → else send the command → query again to verify → bounded retries → exhausted. **Policy when confirmation never comes:** an unconfirmed **pause proceeds with a loud log** (the traversal then runs with TAC active, which is today's behavior); an unconfirmed **run fails the leg to Error with a clear message** (the alternative leaves TAC paused for every later leg, silently). Any error/stop/kill while TAC is paused writes a log line ("TAC left paused"); no restore mechanism is built (the run has failed anyway; TAC resets to paused on reload).
- **Live verification, 2026-09-28, two-character test (`PTAR_multiclass_Erebeth.log`, `PTAR_multiclass_Moxy.log`), route `PTAR_SleepersTombKera.lua` with `tac_before='pause'` on `wp_060` (Drop 1 Water Traverse) and `tac_after='run'` on `wp_062` (Drop 3 Water Traversal), spanning Drop 2 and both navmeshed hallways between drops:**
  - **The key unknown is resolved: PTAR's `mq.event` catches TAC's `[Triune] status:` line live.** Both characters: `TAC status answer: state=running ...` immediately after the query, then `TAC: sending /ac pause ...`, then `TAC status answer: state=paused ...`, then `TAC paused confirmed on attempt 1` — all before `DROP FACE Drop 1 Water Traverse`, i.e. before any facing/fall began. ### DL-014 — Door identity match drops Z: some doors travel far in Z when opening (portcullis-style gates)

- **Status:** Live-verified, build `0.2.0-test.26` (see live verification below).
- **The problem, found live (2026-09-28) during DL-010's second multi-client test:** `Erebeth` (Primary) and `Moxy` (Secondary) at door #44 ("Warder door" / `SHRINEGATE200`, Sleeper's Tomb). `adapter.door_state()`'s identity match requires the live `SwitchTarget` to be within 10 units (3D) of the door's captured position before trusting its `Open()` reading; if not, it returns `nil` ("Target mismatch"), never a real `true`/`false`. Both characters got `Target mismatch` readings with the *Z* component alone off by 11–23 units (X/Y matched closely). Because a Primary's stall fallback advances after 2000ms of an unconfirmed read *without* ever calling `announce_door_open()` (that only fires on a definitively-confirmed `state==true` — [DL-008](#dl-008--multi-character-door-coordination-via-group-chat-primarysecondary-roles) decision #4, an already-agreed, intentional tradeoff, not a defect), Erebeth moved on silently. Moxy, as Secondary, has no equivalent fallback (DL-008 decision #5: never clicks, under any circumstance) and has no other way to detect an open door, so she waited the full 8000ms, failed the leg, retried twice, backtracked once, and hit the identical wall each time — a real, disruptive loop, not a clean quick failure.
- **Developer's fact, confirmed the mechanism plainly:** this door is a gate that retracts *upward*, unlike every other door on this route, which swing. A generic 10-unit 3D tolerance, fine for a hinged door that barely moves, is far too tight for a door whose open state is several times that distance away in Z alone.
- **Evidence gathered before deciding anything (Protocol §4 — verified, not guessed at):** the developer supplied real MQ2Nav door-data files (`reference/MQ2Nav/*.json`) for four zones (Sleeper's Tomb, two Neriak zones, Permafrost), read and compared directly:
  - **Zero door/switch ID collisions in any file** — 33/33 unique in Sleeper's Tomb, 32/32 in Eastern Wastes, 46/46 and 30/30 in the two Neriak files, 36/36 in Permafrost (177 objects total). This directly supports treating `id` (plus `name`, as a cheap extra guard against a stale/failed `/doortarget` selection) as a reliable identity check on its own.
  - **`Type` numbers are per-zone, not a universal door-mechanism code, but every zone checked has at least one distinctly-typed, distinctly-named door-like object that stands apart from its ordinary doors:** Sleeper's Tomb's `SHRINEGATE200` (`Type 77`, the only Type-77 entry in either of the two zones checked for it); Neriak's `HHCELL` (`Type 65`, present in both Neriak files, absent from ordinary `DOOR1`/`DOOR2` entries); Permafrost's `PORT1414`/`PORT2814`/`PORT5628` (`Types 61/66/75`, very likely "portcullis") and `TOGGLE` (`Type 45`). This pattern recurring across four independent zones is why the fix is general, not special-cased to door #44's id or name.
  - **The captured route position for door #44 matches MQ2Nav's own static (closed-state) position closely** (`-791.471,-2383.480,-991.998` both places), confirming the original capture was accurate — the mismatch is purely a live-animation artifact, not a bad capture.
- **Decision:** `adapter.door_state()`'s identity match keeps `id` and `name` equality, keeps the existing player-proximity check (`SwitchTarget.Distance3D()<=35`, unrelated to the door's own position), and keeps X/Y position matching (unchanged 10-unit tolerance) — but **drops Z from the match entirely**, rather than widening it to a new guessed tolerance, since no reliable "how far can any gate travel" number exists across the different gate types found. `Open()`'s value is trusted exactly as before once identity is confirmed; nothing about door-phase logic, retries, or the DL-008 primary/secondary protocol changes — the defect was one level below that protocol, not in it.
- **Implementation:** new pure module [PTARDoorMatch.lua](../lua/PTAR/PTARDoorMatch.lua) (no MacroQuest dependency, mirrors `PTARCombat`/`PTARTac`/`PTARBarrier`'s shape), exposing `matches(observed, captured)` — id/name equality, then X/Y-only distance. `PTAR.lua`'s `adapter.door_state()` now calls it instead of an inline 3D check; the player-proximity check (`distance>35`) is unchanged and checked separately. One incidental fix found while wiring this in: the diagnostic `DOOR target ...` log line used to format `z` with `%.2f` unconditionally — now that `z` is no longer required to be a number for the match to succeed, a `nil`/non-numeric `z` would have crashed that log line; it now formats defensively (`zdisp`).

### DL-016 — Pause PTAR during TAC med breaks; defer waypoint/door barrier timers for the group

- **Status:** Implemented, build `1.1.0-test.1`. Local/simulated validation only — syntax check (27 files) and the full test suite (175 tests, up from 157) pass; nothing here has been run against a live client yet. `PTAR.lua`'s adapter wiring is parse-checked only, per the project's established testing boundary.
- **Story:** as a PTAR user, I want PTAR to wait while a TAC med break is active, just as it currently waits during combat, so travel pauses until the break ends and other running PTAR instances don't start waypoint/door barrier timers while a participant is medding. No specific failure observed; raised proactively. Full story recorded via `User_Story_Template.md`'s process.
- **Requirement:**
  1. PTAR recognizes TAC's own Med Break (the built-in, off-by-default `ctrl.medbreak_enabled` feature) and pauses, the same way it pauses for combat today.
  2. A distinct, UI-visible status, **"Waiting for med break"**, shown while active (mirrors "Waiting for combat").
  3. PTAR's `PTAR:HERE` heartbeat continues unchanged throughout a med break — a medding client is still "actively running PTAR."
  4. PTAR announces to the group when it enters a med break, and separately when it ends.
  5. A waypoint/door barrier timer that has not yet started counting down does not start while any announced med break is active.
  6. A barrier timer already counting down when a med break is announced pauses/extends for the duration of the break — this is a deliberate divergence from combat's existing behavior at a barrier, which does **not** pause the 120000ms clock (see Design choices).
  7. If more than one instance is on a med break at once, deferral persists until all announced med breaks have ended.
  8. An instance that announces a med break and then stops running before announcing completion is handled by the existing ~15000ms heartbeat-expiry roster mechanism (DL-010) — no new timeout.
  9. When a med break ends, PTAR announces completion and resumes, subject to any other active pause condition (e.g. combat active at that moment takes precedence, same as any other phase transition).
  10. Combat-pause behavior is unchanged.
- **Design choices:**
  - **Two distinct signals, kept separate.** *My own* med break is detected locally per character by catching TAC's own console prints via `mq.event` (same pattern as DL-013's `/ac status` catch): start — `[Triune] Med Break -- ...`; end — `[Triune] Med Break over -- ...` or `[Triune] Med Break cancelled -- ...`. Whenever my own flag toggles, I announce it to the group (`/g PTAR:MEDBREAK:START` / `PTAR:MEDBREAK:END`); every instance (including the sender) tracks the resulting set of currently-medding names, filtered by the same live-heartbeat roster DL-010 already uses — satisfying requirement 8 for free.
  - **Two different scopes of effect, matching what the requirements actually say.** *My own* med break joins the exact same interrupt group combat already uses (`nav`/`backtrack`/`door`/`ground_exit`/`barrier_wait`): full pause, new phase `medbreak`, resumes to whichever phase it interrupted (mirrors `combat_return` → `medbreak_return`). *Anyone's* active med break (mine or a groupmate's) additionally gates `barrier_wait` specifically, not ordinary nav/door/ground_exit — a groupmate medding doesn't freeze my travel toward the next waypoint, it only holds up the rendezvous point, per requirements 5/7.
  - **The barrier-clock pause/extend (requirement 6) is a genuinely new mechanism, not a reuse of combat's behavior.** Reading the code confirmed combat interrupting `barrier_wait` today does **not** adjust `self.barrier_started` — the 120000ms clock keeps running through a combat interruption, it just pauses the character's actions. For medbreak, `self.barrier_started` is pushed forward by the paused duration when resuming from `medbreak` back into `barrier_wait`, so the deadline is extended by exactly the time spent on the break. This is an explicit, developer-approved divergence from how combat behaves at a barrier today; combat's own behavior is untouched.
  - **A supplementary end-signal, not relying on TAC's prints alone.** Reading `reference/TAC` source directly (not guessed at, per Protocol §4) found TAC clears `medBreakActive` in five places, only two of which print anything:
    | How it ends | Observable by PTAR |
    |---|---|
    | Thresholds met (normal case) | prints "Med Break over -- resuming." |
    | Attacked (break cancelled) | prints "Med Break cancelled -- ...!" |
    | Aggro-switch event mid-combat (`checkAggroSwitch`, silent) | no print, but TAC calls `/stand` if sitting/ducking |
    | Feature disabled while active | no print, but TAC calls `/stand` |
    | **TAC's own mode is switched while medding** (`setTriuneMode`) | no print, no stand — nothing observable |
    PTAR therefore also watches `Me.Sitting()`/`Me.Ducking()` transitioning from true to false while its own `medbreak_active` flag is set and no explicit end-print has fired, closing the aggro-switch and feature-disabled gaps using a signal that is TAC's own direct physical action, not a derived judgment — this matters because an earlier idea (treating PTAR's own `io.combat()` going true as an implicit end signal) was considered and **rejected**: `PTARCombat.lua`'s `active` definition counts any group-shared XTarget hostile, the same broad signal TAC's *strict* (non-ignore-group) mode uses to cancel a break; with "Ignore Group Combat While Medding" enabled (the developer's own normal configuration), TAC deliberately rests through exactly that condition, so `io.combat()` cannot be trusted as a stand-in for "the break ended" without false-triggering on ordinary group combat.
  - **Confirmed, not assumed: no restart flip-flop risk after a cancellation.** Read directly from source: a new break only starts when `not medBreakActive` *and* the metric is back at or below the **start** threshold, never the stop threshold — so a break cancelled by an attack at, say, 40% mana will not restart until mana actually drops back to the configured start threshold (e.g. 20%), confirmed against the developer's own stated example. An end-signal firing can be trusted as a real, lasting return to normal operation, not a flicker.
  - **One known, accepted gap: the mode-switch case (requirement 9's "no new timeout" spirit extended here too).** Switching TAC's own mode away from Manual while a med break is active produces no observable signal at all (no print, no stand). Given PTAR's whole design assumes every character stays in TAC's Manual mode for the entire run (DL-010), this requires someone to deliberately reach into TAC's mode control mid-route — **developer decision, 2026-10-02: accept as a known limitation, no bounded-timeout fallback.** If it occurs, the affected client stays in `medbreak` phase until manually recovered (Pause/Resume or Stop/Start). Revisit only if this is actually observed live, per Protocol §15's standard for timing/stall values (which this deliberately is not adding).
- **Implementation choices:** message names `PTAR:MEDBREAK:START`/`PTAR:MEDBREAK:END`; phase name `medbreak`; status text `"Waiting for med break"`; new `PTARBarrier.lua` methods for a toggle-able active-medbreak set (distinct from `REACHED`'s monotonic set, since a break can start/stop more than once per run); exact `mq.event` patterns for the three TAC print variants, mirroring the existing `#*#[Triune] status: ...#*#` wildcard shape.
- **Deliberately deferred:** no PTAR-side control to trigger a med break — TAC owns that decision entirely, PTAR only observes; no handling beyond the three known TAC print phrasings (a future TAC wording change would need revisiting, not solved here); no change to `BARRIER_TIMEOUT_MS` itself, only to how its elapsed time is computed.
- **Open:** none blocking implementation. The mode-switch gap above is accepted, not open.
- **Implementation (2026-10-02, build `1.1.0-test.1`; local/simulated only, nothing live-verified yet).** Tests first throughout, each shown failing for the right reason before the code, per Protocol §7.
  - **`PTARBarrier.lua`:** `mark_medbreak`/`clear_medbreak`/`medbreak_active_names` — a toggle-able set, separate from `REACHED`'s monotonic one. 8 new tests, mutation-checked (a mutation that ignored the candidate-list filter and returned the raw internal set was caught).
  - **`PTARRunnerCore.lua`:** `io.medbreak()` (own) joins the exact combat interrupt group (`nav`/`backtrack`/`door`/`ground_exit`/`barrier_wait`), new phase `medbreak`, `medbreak_return` mirrors `combat_return`. `check_barrier()` checks `io.medbreak_group_active()` first, before the roster/seen logic, covering both "not yet started" and "already running" with one check. On resuming from `medbreak` back into `barrier_wait`, the paused duration is added onto `self.barrier_started` — mutation-checked (removing that line, or swapping the group check for the own-only check, were both caught by dedicated tests). `heartbeat_active()` and `tick()`'s own top-level status gate both needed `'Waiting for med break'` added — **a real bug found by the tests themselves**: the first version left `tick()`'s entry gate unchanged, so every tick after entering the status was silently a no-op and the phase never cleared; the resume tests caught it immediately. 10 new tests, mutation-checked.
  - **`PTAR.lua` (parse-checked only):** `mq.event` registrations for TAC's three console-print variants (start, over, cancelled) and the new `PTAR:MEDBREAK:START`/`END` group messages; `check_medbreak_stood()` polls `Me.Sitting()`/`Me.Ducking()` as the fallback for the one silent-but-standing TAC clear path (`checkAggroSwitch`), gated by a `MEDBREAK_GRACE_MS=3000` first-guess (Protocol §15) so it can't fire during the brief window before TAC's own `/sit` actually lands.
  - **One subtle, harmless finding from self-review, recorded for honesty rather than left implicit:** `adapter.medbreak_group_active()` filters against `adapter.barrier_roster()`, which (per DL-010's live-confirmed fact) excludes the local character's own name. This means a client's own active break is briefly invisible to its own group-active check — in practice this doesn't produce incorrect behavior: the client's own `io.medbreak()` (local flag) already catches its own break on the very next tick via the ordinary interrupt-group path, and every *other* client's `barrier_roster()` correctly includes this client's name, so requirement 7 (deferred until all have ended) holds correctly from everyone else's perspective. At most a one-tick (~100 ms) self-referential inconsistency, self-correcting without intervention. Not changed, since there is nothing for it to incorrectly block in practice — flagged here in case it ever matters for a future change to this area.
- **Live verification, 2026-10-02 (`PTAR_multiclass_Kateri.log`, build `1.1.0-test.2`, Solo mode, single character):** a real TAC med break interrupted nav (`Waiting for med break: Med break interrupted Warder NE; keeping the current waypoint and retries.`, START line caught 08:57:27), lasted about 74 s, then the END line was caught (08:58:41), logging `Med break clear; resuming nav toward Warder NE`, re-issuing `/nav`, and returning to Running. Confirms requirements 1, 2 and 9 for the solo path, and that TAC's console lines are caught live by the new `mq.event` patterns. The log does not record which end line fired (over vs. cancelled). **Not yet live-tested:** the multi-character requirements (5, 6, 7: barrier deferral, clock extension, all-must-end), the Sitting/Ducking fallback, and the barrier-wait interrupt. Those need Group mode with at least two characters.

DL-017 requirement 2 says no group-chat announcements of any kind in Solo; the heartbeat, waypoint-reached and door-open sends were gated, but `set_my_medbreak()` (added here) was missed. ### DL-017 — Solo and Group modes: a per-character setting that silences group coordination entirely in Solo

- **Status:** Implemented, build `1.1.0-test.2`. Local/simulated validation only — syntax check (28 files) and the full test suite (184 tests, up from 175) pass; nothing here has been run against a live client yet. `PTAR.lua`'s adapter/UI wiring is parse-checked only, per the project's established testing boundary.
- **Story:** as a PTAR user, I want to choose Solo mode or Group mode, so PTAR behaves appropriately when running alone versus coordinating with other PTAR instances, while preserving Group-mode settings across the switch. Full story recorded via `User_Story_Template.md`'s process; a UI mockup was supplied showing the proposed Mode toggle and Settings layout.
- **Requirement:**
  1. The user can select Solo mode or Group mode in the Runner UI.
  2. In Solo mode, PTAR treats itself as the only running instance: **no group-chat announcements of any kind go out** — heartbeat, waypoint-reached, and door-open are all suppressed, since all three exist solely to facilitate Group-mode coordination. In Solo mode PTAR does not wait on any other instance or its barks.
  3. Any setting meaningful only in Group mode is hidden entirely in Solo mode, not shown read-only — a general rule, not special-cased to one control. Today that's only Door Opening Role; a future group-only setting follows the same treatment without a fresh discussion.
  4. Switching to Solo preserves the character's Group-mode settings (Door Opening Role) for later; switching back to Group restores and uses them, unchanged.
  5. Group mode retains today's existing heartbeat/coordination behavior, unchanged.
  6. Combat and med-break pauses (DL-016) work unchanged in both modes.
  7. Mode persists per character/server between sessions, same as `last_route`/`door_role`/`echo_enabled` today.
  8. Default mode is **Solo**, for every installation — new and existing alike, no special-casing by whether a settings file already exists. (Developer's own context: Group mode has observed reliability issues and is being treated as beta; Solo is the reliable, fully-tested path.)
  9. The first time this version runs, a one-time, **blocking** modal explains that Group mode is currently beta, Solo is the default/recommended mode, and that this setting is **local to this character only** — it never affects any other PTAR instance, each of which sets its own mode independently. Shown exactly once, ever, regardless of which mode is ultimately chosen — not re-shown every session, and not tied to whether the user ever switches to Solo. The developer's own framing: this is to be able to say "we clearly communicated this," not to badger the user into compliance.
  10. Mode switching is blocked while Running/Recovering/Waiting for combat/Waiting for med break — the same guard already applied to the Route selector — requiring Pause or Stop first.
- **Design choices:**
  - **Solo mode needs no new logic in `PTARRunnerCore.lua` at all.** `check_barrier()` already has a fully-tested "empty roster releases immediately" path (DL-010's own solo-run test). Making `adapter.barrier_roster()` return an empty list whenever mode is Solo — regardless of actual in-game group membership — makes every barrier wait resolve instantly through that existing path. Since `medbreak_group_active()` (DL-016) already derives from the same roster, it falls out empty for free too, satisfying "no waiting on other instances" without touching either module's tested logic.
  - **Group-chat suppression happens in the adapter, not the runner.** `PTARRunnerCore.lua` keeps calling `io.barrier_announce()`/`io.announce_door_open()` and the main loop keeps evaluating the heartbeat send exactly as before and unconditionally — DL-010's "bark unconditionally on arrival" invariant (a client that miscounts must never withhold its own bark) stays completely intact and untested-for-regression-risk. In Solo mode, the **adapter** implementations of those functions skip the actual `mq.cmd` chat send, while still logging what would have been sent (developer's own call: "very small overhead that could still be useful diagnostically").
  - **Door Opening Role is overridden at the read site, not mutated.** `adapter.door_role()` returns `'primary'` whenever mode is Solo; the real stored value is only read in Group mode and is never touched by switching modes. This is what makes "switching preserves/restores Group settings" come for free rather than needing explicit save/restore logic — there is nothing to restore because nothing was ever overwritten.
  - **The one-time modal's job is proof of notice, not enforcement.** No mechanism prevents a user from dismissing it without reading it — per the developer, that's an accepted, deliberate tradeoff: "we can only give you the information, we can't force you to read it."
  - **No technical enforcement needed for the "this is per-instance" concern.** Investigated and confirmed: nothing in this design (or any prior PTAR feature) gives one PTAR instance any way to write to or affect another instance's settings — `door_role` and the new `mode` field are both purely local, and barks are read-only signals other instances observe, never a configuration channel. The risk the developer raised is a user *mental-model* risk (the wording "Group mode" could be misread as a group-wide action), not a functional one — addressed by the modal's and Settings section's wording, not by new logic.
- **Implementation choices:** new `PTARSettings.lua` fields `mode` (`'solo'`/`'group'`, default `'solo'` if absent) and `seen_mode_notice` (boolean); exact ImGui modal-popup calls (`OpenPopup`/`BeginPopupModal`/`CloseCurrentPopup` or MacroQuest's Lua binding's equivalent) to be confirmed against what the binding actually exposes, not assumed; Mode toggle placement in the Runner UI per the supplied mockup (a row above Route, two buttons).
- **Deferred, not part of this story:** the *existing* Route-selector/Refresh-Routes guard only checks Running/Recovering/Waiting for combat — it was never updated to also block during "Waiting for med break" when DL-016 added that status. This is a pre-existing gap, unrelated to mode-switching; the *new* mode-switch guard is built correctly (including med break) rather than copying it, but fixing the older guard is left as a separate decision, not bundled into this build (Protocol §6).
- **Implementation (2026-10-02, build `1.1.0-test.2`; local/simulated only, nothing live-verified yet).**
  - **`PTARSettings.lua`:** two new fields, `mode` (`'solo'`/`'group'`, invalid values rejected the same way as `door_role`) and `seen_mode_notice` (boolean, `nil` when never set so the modal correctly shows on first run — distinct from `false`). 9 new tests, mutation-checked (dropping the `mode` validation line was caught).

### DL-018 — Compact window mode: a three-row view for monitoring and operating PTAR in less screen space

- **Status:** Implemented, build `1.1.0-test.5`, not yet committed or live-tested. Acceptance criteria approved by the developer 2026-10-02 ("Approved"); design proposed and approved the same day with one correction (see Design choices). Local/simulated validation only: syntax check (28 files) and 198 tests (up from 184) pass; the compact/full UI in `PTAR.lua` is parse-checked only and needs a live check.
- **Story:** as a PTAR user, I want a smaller, usable window with route selection, status and essential operating controls, so I can monitor and control PTAR while using less screen space. Source: developer's user story and approved layout screenshot (full view and compact view), 2026-10-02.
- **Requirement:**
  1. Full view gains a **Compact** button at the upper right of the Mode row. Selecting it opens compact view.
  2. Compact view has three rows: the Route selector; the current Status; and Start, Pause/Resume, Stop and a **Full** button (Full at the right of that row). Selecting Full returns to full view with every control available.
  3. Compact view is smaller than full view while keeping the route, status and operating controls readable and reachable. Minimum possible size is not the goal.
  4. The route selector keeps its existing fixed-width display behavior; the selected route is visible and selectable.
  5. Start in compact view uses the start method and waypoint last selected in full view.
  6. Pause/Resume is one toggle button (developer-approved 2026-10-02). While Running, Recovering, Waiting for combat or Waiting for med break it reads "Pause" and does what Pause does today. While Paused it reads "Resume" and does exactly what "Resume at nearest valid" does today, including being disabled during TAC and traversal phases. In any other status (Ready, Completed, Error, Manual handoff) it is disabled.
  7. Compact view does not show the Solo/Group mode or any control to change it; those stay in full view. Waypoint selection, start-method selection, settings, log information and help text also stay in full view only.
  8. Switching views changes presentation only: the selected route, waypoint, start method, settings and current operating state are preserved, and combat pauses, med-break pauses and Solo/Group behavior are unchanged.
  9. PTAR remembers the selected view between sessions and opens in the one used last.
  10. **Compact view is deliberately quiet (developer decision, 2026-10-02): it does not show the "PTAR is setting TAC…" or "mid-traversal…" notes explaining why Start/Resume is disabled, nor other progress messages. A user who wants the reason switches to full view.** This is a scoped exception to DL-013's developer requirement that a blocked Start/Resume must be visibly explained: **SUPERSEDES DL-013 (block-message visibility) in compact view only; full view is unchanged.**
- **Design choices (developer-owned):** the two approved layouts (screenshot) and the Pause/Resume toggle (req 6). A brand-new install with no saved view opens in **full** view. **Returning to full view restores the window size the user had in full view when they went compact** (developer correction 2026-10-02; my first proposal was a fixed 560x390 reset, which the developer rejected).
- **Implementation choices:** `view` setting (`full`/`compact`) in `PTARSettings`, invalid values ignored; `PTARRunnerCore:pause_resume_state()` returns `pause`/`resume`/`disabled` from status alone so req 6 is unit-tested (mutation-checked: breaking the Paused case and the Waiting-for-med-break case each failed exactly the matching test; removing the settings validation failed the invalid-value test); in `PTAR.lua`, shared `route_selector()` and `do_start()` used by both views so Start and the route guard behave identically, `draw_compact()`, `set_view()` which logs `View set to <view>`, and a one-frame `ImGuiCond.Always` size on each switch. Full size is read with `ImGui.GetWindowSize()` (used by the developer's other Project Triune scripts, not found in the TAC reference) inside a `pcall`; if it cannot be read the previous/default 560x390 is used and the log says so. Compact is first-guess 520x120 (tunable live). Compact/Full buttons are right-aligned with `GetWindowWidth()` minus a fixed offset (88/60 px, first guesses) inside a `pcall`. The compact Pause/Resume button reads `Pause`, `Resume`, or `Pause/Resume` when disabled (the approved screenshot shows that label at Ready), so the button width changes when the label does. The session-start log line now includes the view. Unverified until live: `GetWindowSize`'s return shape, right-alignment offsets, and window sizes.
- **Live-confirmed 2026-10-02 (developer, build `1.1.0-test.5`):** Compact and Full switching, the full-view size restored after a round trip, the view remembered across a restart, and the button alignment and sizes. **Log evidence (`PTAR_multiclass_Kylaeris.log`):** session started `view full` 10:32:21; `View set to compact` 10:32:30; `View set to full` 10:32:34; `View set to compact` 10:32:50; session restarted `view compact` 10:32:59. No `Could not read the full-view window size` line, so `ImGui.GetWindowSize()` returned a usable size in this MacroQuest build. Not separately observed: Pause/Resume in each status and the quiet-compact behavior during a run (developer confirmed items 1-4 of the live check only).
- **Layout refinements after live review, 2026-10-02 (developer direction; builds `1.1.0-test.5` to `1.1.0-test.9`):** all of these refine requirements 2-4 and were confirmed by the developer ("Perfect") on `1.1.0-test.9`. (a) The button is labeled **Full Mode** and sits immediately after Stop with normal spacing, at a position independent of window and dropdown width (the earlier alignment of Full to the dropdown's right edge was removed). (b) **Requirement 4 clarified for compact view:** the Route dropdown is no longer a fixed share of the window; it grows and shrinks with the window between a minimum of 240 px and the width of the full-view Route dropdown (measured there), so widening grows it first and narrowing removes empty space first, then shrinks it. Full view's dropdown is unchanged. (c) Compact height is locked to its content (`SetNextWindowSizeConstraints`, wrapped; logs `Compact height lock unavailable` if the call is missing) while width stays manually resizable; the minimum window width is the minimum dropdown plus the whole button row plus padding, and the default width is that minimum. (d) The Pause/Resume button keeps one width (that of its longest label, derived from the Start button's frame padding and `CalcTextSize`) so Stop and Full Mode never shift. Implementation choices, tunable live: the 240 px minimum, 6 px height margin, 8 px edge padding.
- **Compact Start changed, developer decision 2026-10-02, build `1.1.0-test.10`: SUPERSEDES DL-018 requirement 5 (compact view only).** Compact view's Start always starts at the nearest valid waypoint (the same action as Start with "At Nearest Valid Waypoint" and as Resume), ignoring the start method and waypoint selected in full view. Full view's Start is unchanged and still uses the selected method. Local validation only (the nearest-valid start is covered by existing tests; the compact wiring is parse-checked); not yet live-confirmed.
- **Open:** none known. Risk if it goes wrong, per the story: essential controls or status become hard to reach, or switching views loses a selection or interrupts operation; severity is the developer's to assess.
